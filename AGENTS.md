## Project rules

- Managed-account avatars use the existing private candidate-photos path candidate-drafts/<userId>/agent-profile.jpg; admin uploads and owner uploads share it so every authorized view resolves the same image.
- App data is read client-side via the browser data client + TanStack Query options in `src/lib/data.ts`; all pages live under the `_authenticated` layout — keeps one cached dataset so search/filters/stats update instantly.
- Exam results live on the exam row; a DB trigger appends every non-pending result change to the results history table — history is never overwritten.
- Official SVP result lookup goes only through `src/lib/svp.functions.ts`; manual non-SVP lookup remains isolated in `src/lib/result-checker.ts` — prevents duplicate external-result implementations.
- TS strictness flags noUncheckedIndexedAccess/exactOptionalPropertyTypes/noImplicitReturns/noPropertyAccessFromIndexSignature are off — they conflict with recharts/shadcn typings and add noise.
- Customer login is mobile number + password on /auth, signing in with a synthetic email `88<mobile>@phone.login.local`; no OTP in the login flow — phone provider unavailable, so phone maps to email credentials.
- Customers (no user_roles row) land on the neutral /portal. `get_customer_portal` returns only a whitelist of their own candidate, released/paid exam results and receipts; customers cannot select internal base tables or staff/agent contact information. Customer pages, shared login/reset and loading states have no institutional branding. Staff-table policies use is_staff(). Most management pages (_authenticated) require admin/staff; the Takamol availability page and SVP booking workspace also allow agents, with agent booking rows limited to records created by that agent. Admins sign in at /admin/login with email/password — keeps phone-OTP customers out of the dashboard.
- SVP (Saudi Skill Verification) result lookup runs server-side in `src/lib/svp.functions.ts` (staff-only), nationality fixed to Bangladesh (BGD); results update the exam row so history trigger logs it.
- Applicant result visibility is gated by candidates.result_check_at and served publicly only via the SECURITY DEFINER RPC check_applicant_result (passport + occupation) — exposes one matching record, never the table.
- Roles: admin/staff oversee all management pages; agent → /dashboard + /submit-job + /my-works + read-only /takamol availability + own-record /svp-booking; service_provider → /provider; management → /management reception; no role = customer /portal. Managed-account details + active flags live in agent_accounts, and every role is server/RLS enforced.
- Approved submissions are the workflow source: database triggers link them to candidate/exam records and synchronize SVP results to the exam history, while the management role only handles reception details — keeps every role on one authoritative record.
- "Reception + Agent" accounts are stored as two user_roles rows (management + agent) with agent_accounts.role=management — reuses existing per-role RLS and routing instead of a new role.
- Device + 12h login is enforced via `src/lib/device-session.ts` against `device_sessions` through SECURITY DEFINER RPCs claim/is_current_device_session; admins keep the latest two device keys (session_key + prev_session_key), other roles one — newest login wins, oldest is signed out on next check.
- Sub-agents are agent accounts with agent_accounts.parent_agent_id; their submissions start as status pending_agent (set by insert trigger), visible only to parent agent and admin until the parent approves into pending_approval — reuses the normal agent workflow and RLS.
- Admin messaging: recipient selection and template rendering live in src/lib/messaging.ts (shared by preview and sender); sending goes through a sms_messages queue with unique dedupe_key, processed by admin server fns and an hourly cron route — one sender path, no duplicate SMS.
- The /svp-booking workspace (agent-only; admins/staff use the management systems): `SvpBookingWizard` runs the real booking flow — `SvpLoginPanel` signs in through `src/lib/svp-session.functions.ts` (`/sessions/login` → `/sessions/otp`) and `src/lib/svp-session.server.ts` keeps the SVP bearer token + refresh cookies in an httpOnly per-app-user cookie; `svp-booking.functions.ts` then calls occupations → test-center cities → `validate` eligibility → `available_dates` → `exam_sessions` → `POST exam_reservations` → free reservations or `reservation_credits/use`. The old manual-entry panel is removed; a successful reservation still writes one local `svp_bookings` row (candidate name + passport are required in the confirm step, agents see only their own rows). Occupation search uses `searchSvpOccupations` (SVP `name` query) behind a debounced similar-occupation dropdown. Ticket PDFs are proxied by `downloadSvpTicket` (`/tickets/{id}/show_pdf`) and saved as `<system name>_<occupation English name>_SVP_Ticket.pdf`. Up to four SVP accounts are stored in one httpOnly vault cookie (`src/lib/svp-session.vault.ts`); `listSvpAccounts` / `switchSvpAccount` / `removeSvpAccount` switch the active token without another password/OTP, and every SVP call uses the active account. The SVP password is stored AES-GCM encrypted in the same vault (key from `SVP_CREDENTIAL_KEY`, falling back to `SUPABASE_SERVICE_ROLE_KEY`) so the Reconnect button requests a fresh OTP and only `submitStoredSvpOtp` finishes it; the password never reaches the browser. `fe_app`/`otp_method`/`locale` are server-managed, credentials are redacted from messages, and tokens never reach the browser. `getSvpAccountOverview` exposes the real `/permissions` keys, `/exam_constraints` (reschedule quota, seat-hold seconds, cancellation limit) and flipper flags, and the wizard drops back to login whenever any SVP call reports an expired/revoked session. Rescheduling loads `/exam_reservations/{id}`, fetches `available_dates` with `reservation_id` (+2 days), holds the new seat via `/temporary_seats`, then calls `POST /exam_reservations/{id}/reschedule` with `{ id, exam_session_id, language_code }`; the local `svp_bookings` row is updated with the new date/time/center. Real targeted sessions are date-only load-balancer tokens: hold **all** session ids for the date via `POST /temporary_seats` (`exam_session_id: [ids]`, `country_id`, `category_id`), read the assigned `exam_session_id`, fetch `/exam_sessions/{id}`, then create the reservation with that id (omit `duration`/`start_at` when SVP does not return them). Targeted cities come from `available_dates` (`/test_centers/cities` is site-based only) and languages are `non_targeted = false` prometric codes (prefer the 30-question code for CBT); GET 429/5xx (including 529) are retried. Targeted bookings create the temporary seat before confirmation (`POST /temporary_seats` with `exam_session_id`, `country_id`, `category_id`) and re-hold it best-effort right before `POST /exam_reservations`. Site-based (non-targeted) countries book through `/prometric_scheduling/sites_availabilities` → `/prometric_scheduling/slots_availabilities` (site_ids[] + exam_id) → a slot hold (`POST /prometric_scheduling/slots_availabilities`) → `POST /exam_reservations` with the prometric `exam_id`, `site_id`, `site_city` and `hold_id`; site-based reschedules hold the new slot (`POST /prometric_scheduling/slots_availabilities`) and then POST the reschedule with the prometric `exam_id`, `site_id`, `site_city` and `hold_id`, retrying once with the slot id if SVP rejects that shape.
- Live SVP contract verified: `POST /temporary_seats` requires `methodology: in_person` — without it SVP returns `exam_session_id: 0` (a broken hold); the response's `exam_session_id` is the **assigned session token to book** (it can differ from `/exam_sessions/{id}`), and `expired_at` is `dd/mm/yyyy HH:MM`. Every request sends `X-Tenant-Name: svp-international`.
- Passed SVP results expose `exam_result`/`final_result` + `examination_result` scores and an issued `certificate { id, certificate_number, status, valid_until }` on the reservation detail; `downloadSvpCertificate` proxies `/individual_labor_space/certificates/{id}/show_pdf` and the file is saved as `<candidate>_<occupation>_<test center>_SVP_Certificate.pdf`. Finished reservations enrich themselves from the detail endpoint so the result panel and certificate button appear even when the list omits them.
- SVP exposes no CBT-result PDF endpoint (only `/tickets/{id}/show_pdf`, `/certificates/{id}/show_pdf`, `/invoices/{id}/show_pdf`), so the CBT result sheet is generated locally by `src/lib/svp-result-pdf.ts` (dependency-free PDF writer) from the real reservation result and saved as `<candidate>_<occupation>_<test center>_SVP_CBT_Result.pdf`; the certificate PDF still comes from SVP.
- Step 1 now holds occupation, the Takamol language and the available **city dropdown**; the SVP category is resolved silently and is never shown as UI. Step 2 starts with the available dates and loads the test centers/sessions for the chosen date (no city field there). The date must be picked before a test center can be selected.
- The exam language is a **manual, required** choice in Step 1 (no auto-selection, no auto-advance); a single **Continue** button runs the eligibility check and only advances to Step 2 when every check passes — no background eligibility checks. Exception: when Takamol returns one `language_code` for the occupation, that single language is shown and applied automatically; if Takamol omits it the SVP occupation/category prometric codes are offered, and when SVP has none either the operator can type the SVP language code — a missing Takamol code never blocks booking.
- Step 2 dates use the click-to-open `SvpDateCalendar`: dates SVP reports with free seats are highlighted (with seat counts), choosing one closes the panel and clicking the field reopens it. The placeholder "Not provided by SVP" session table is gone; when the Takamol API returns no rows the SVP sessions render as compact cards instead.
- Native targeted session ids are re-encrypted on each read and may contain only date/city. `listSvpExamSessions` resolves a complete date's availability through the configured Takamol sessions gateway (5s, no retries), keeping each resolved row's own SVP token together with its center/time/seats; never zip the two APIs by position or require their independent live counts to match. A complete gateway catalogue must have valid details for every row for the requested date/city/category. Resolved targeted rows keep `siteId: null` so center ids do not switch booking into the prometric flow. Incomplete resolution falls back to the native tokens.
- Card payment UI: `SvpCardPayment` calls `startSvpReservationPayment` (server), mounts the official gateway widget (`<form class="paymentWidgets" data-brands="VISA MASTER">` + `${hyperpay_url}/v1/paymentWidgets.js?checkoutId=…` with `wpwlOptions`), posts back to `/svp-booking?paymentId=…`, and verifies that id with `getSvpPaymentStatus` (`PUT /payments/{id}`). A payment-required reservation opens the secure widget automatically in a new tab (`/svp-booking?payReservation=<id>` → `SvpPaymentPage`, which auto-starts the checkout and verifies the posted-back payment id there), while the wizard keeps the inline widget as a fallback. The payment tab renders in a light `svp-payment-page` scope and the holder uses `svp-card-widget` CSS overrides so gateway labels/inputs stay white with dark text on the app's dark theme. Card data never touches this app.
- CBT result PDF fee: `settings.cbt_result_fee` (default ৳50, editable from the admin control centre) is charged once per reservation by `wallet_charge_cbt_result` before `src/lib/svp-result-pdf.ts` generates the file; the wallet balance and the fee are shown on the download button.
- Pending (draft) SVP bookings expire automatically: `cancel_stale_svp_bookings(30)` marks unpaid drafts cancelled, called on app load (throttled) and from `/api/public/cron/svp-pending-cancel`.
- Wallet/deposit: `wallet_accounts`, `wallet_transactions` and `wallet_deposits` back the /wallet page; agents, staff and sub-agents request deposits, admins/staff approve them (`wallet_review_deposit`) and can adjust balances (`wallet_admin_adjust`). Every SVP booking charges ৳100 with `wallet_charge_booking` (idempotent per reservation) and the booking/history UI shows the fee and remaining balance.
- RSPay gateway controls live in `rspay_gateway_settings` (master defaults off, per-method preferences for bkash/nagad/rocket/upay). Only admins can change them through `set_rspay_gateway_control`, with atomic per-control changes and an audit log. The deployment flag `RSPAY_AUTO_DEPOSIT_ENABLED` remains authoritative; admin controls cannot bypass server activation. The server and `wallet_rspay_begin` reject disabled methods for new orders. Existing callbacks and wallet settlement remain independent of these switches.
- SVP route coverage: every labor-space route the portal uses is implemented server-side — permissions, occupations, exam constraints/sessions/session-by-id, available dates, test-center cities, temporary seats, reservations (list/detail/create/delete/reschedule), reservation credits, certificate price, payments (list/detail/create/verify/validate pending), notifications, feature flags (labor-space primary, `/flipper` fallback) and user balance (`/user_balance/{id}` primary, `/users/{id}/balance` fallback). The wizard surfaces payments + notifications in the account activity panel and cancels reservations through the DELETE route.

- Smart Appointment uploads read PDFs with PDF.js and recognize scans locally with bundled English OCR assets (`build/ocr-assets.ts`). `ticket-extraction.ts` owns parsing/normalization and unambiguous catalogue matching; all valid HH:mm exam times are accepted. No AI key is required for this form. Unreadable valid uploads allow manual completion. Reference occupations/centres come from the verified Takamol catalogue migration; existing admin edits are preserved. Tickets/photos use the private candidate-photos bucket with role/path access policies.
